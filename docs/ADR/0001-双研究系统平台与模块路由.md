# ADR-0001：双研究系统平台与模块路由

- 状态：已接受
- 日期：2026-09-29
- 决策人：项目著作人
- 关联需求/问题：在同一软件主体中容纳多准则决策与后续自适应评估研究
- 替代/被替代 ADR：无

## 背景

软件计划承载两项来源、数据口径和建设进度不同的学生研究。多准则决策系统已有可运行代码与归档数据；自适应评估研究材料尚未提供。入口必须让用户先选择研究方向，同时避免为第二项研究编造指标、流程或接口，并保留多准则工作台中的未保存草稿。

## 决策驱动因素

- 两项研究共享品牌、启动方式与工程质量门禁，但业务状态和方法必须隔离；
- 当前只允许多准则模块调用其 API，自适应模块仅能说明建设状态；
- 本机单体部署应保持简单，刷新、前进后退和未知地址需要稳定；
- 后续接入第二项研究时，应能在不重写现有模块的前提下新增独立实现。

## 备选方案

### 方案 A：平台入口加同仓模块路由

使用 Vue Router 的 `/`、`/mcdm`、`/adaptive` 三个 Hash 路由。平台只依赖模块注册表；多准则模块懒加载并用 `KeepAlive` 保留编辑状态。两项研究共享基础视觉令牌与品牌组件，各自拥有页面、状态和 API 边界。

优势是部署与启动简单、现有代码迁移量可控、模块边界可由测试和静态契约验证。代价是共享同一个前端构建，模块团队未来需要遵守仓库级接口约束。

### 方案 B：工作台顶部直接切换研究

把第二项研究作为现有侧栏或顶部标签。实现较快，但会把平台选择、研究上下文和页面导航混在一起，也容易让未完成模块看起来已经可用。

### 方案 C：独立微前端或独立站点

隔离最强，但当前只有单机演示、一个已实现模块，额外的部署、通信、版本协调和故障边界没有收益依据。

## 决策

采用方案 A。`src/platform/modules.ts` 是模块名称、状态、入口路径和强调色的单一事实来源；`src/router/index.ts` 只负责平台级路由装配，不导入多准则 workspace 或 API。多准则模块由 `McdmWorkbench.vue` 独占 workspace 实例。自适应路由当前仅渲染规划说明，不请求 `/api`、不出现可执行评估控件。

模块切换放在平台入口和多准则壳层的“返回研究平台”链接中，不把第二项研究塞入多准则业务导航。当前不采用微前端；只有当两个模块需要独立发布节奏、不同运行时或独立团队权限时才复审。

## 后果

### 正向

- 用户能在进入业务工作台前识别两个研究方向及各自状态；
- 自适应研究未接入时仍保持事实准确；
- 多准则数据、草稿和 API 不泄漏到平台入口或自适应模块；
- 后续可通过模块注册表和独立路由扩展第二项研究。

### 代价与风险

- `KeepAlive` 会保留多准则工作区内存状态，退出模块不等于放弃草稿；
- 共享基础样式的变更可能同时影响两个入口页，需执行三档浏览器回归；
- 单构建产物中的 ECharts 懒加载块目前约 531 kB，构建会提示体积警告。

### 后续工作

- 收到自适应研究材料后先审核业务对象、输入输出、数据授权与评估口径；
- 为自适应模块建立独立状态、API、测试与 ADR，不复用多准则结果作为演示数据；
- 独立发布需求出现时再评估微前端或多应用部署。

## 验证与回退

路由单元测试验证直接访问、未知地址和模块元数据；设计契约检查模块隔离；真实浏览器验证返回/前进/刷新、草稿保留、三档布局和零横向溢出。若共享构建造成实际发布阻塞，可保留模块注册契约并拆成两个构建入口，不需要改变研究数据模型。

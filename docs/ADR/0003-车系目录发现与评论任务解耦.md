# ADR-0003：车系目录发现与评论任务解耦

- 状态：已采纳
- 日期：2026-10-09
- 决策范围：汽车之家新能源车系目录与评论采集任务

## 背景

旧流程在每个评论任务内部重新发现“前 N 个车系”。用户无法在启动前查看或选择对象，重复任务会重复扫描目录，目录变化也可能改变正在运行任务的输入。目录发现和评论采集还共享同一外部数据源，需要明确互斥、失败恢复和版本边界。

## 决策

将流程拆成两个独立阶段：

1. `SeriesCatalogService` 在后台发现按 `platform + series_id` 去重的前 1000 个唯一车系，写入暂存批次；成功后用单一事务更新活动目录指针。失败或取消清理暂存数据并保留旧目录。
2. 用户从活动目录中显式选择车系。创建评论任务时，后端在同一事务中重新校验活动目录并写入规范化、不可变的 `collection_job_series` 快照；任务只消费该快照。

目录发现和评论采集通过同一个 `ExternalAccessCoordinator` 预约外部访问。读目录、历史任务、已保存评论和导出不占用预约。升级前的任务可从 `series_manifest` 只读恢复，但新任务不再写入或依赖该字段。

前端由 `catalogFlow.ts` 独占目录轮询、搜索、跨页选择和任务创建状态；通用 `workspace.ts` 继续负责评论任务控制和已采集资产查询。界面采用“01 发现车系 / 02 选择并采集”两步结构。

## 备选方案

- 打开对话框时同步发现：一次扫描可能超过 HTTP 生命周期，页面关闭后难以显示进度或取消，因此不采用。
- 创建评论草稿任务后再发现：会把可选目录、用户选择和任务状态绑定在一起，刷新目录容易影响任务输入，因此不采用。
- 继续在每个任务内隐式发现：实现改动最少，但不能满足显式选择、目录复用和输入可追溯，因此不采用。

## 结果与约束

- 目录可以独立刷新、取消和复用；旧目录在新批次发布前持续可用。
- 评论任务输入在创建后稳定，可审计到目录批次、发现顺序和选择顺序。
- 多一个目录状态机和三张目录表，但职责、事务边界和恢复路径更清楚。
- 两个后台服务仍是本机单进程能力，不是分布式锁；多实例部署前必须重新设计协调机制。
- 真实来源出现结构漂移时必须失败并保留旧目录，不降低结构保护阈值或使用模糊选择器猜测数据。

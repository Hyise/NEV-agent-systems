# ADR-0002：评论采集作为独立平台子系统

- 状态：已接受
- 日期：2026-10-08
- 决策人：项目著作人
- 关联需求/问题：为多准则与未来自适应研究提供可追溯的汽车评论数据资产
- 替代/被替代 ADR：扩展 ADR-0001 的平台模块注册方式，不替代其历史决策

## 背景

多准则研究需要从汽车评论中提取准则，未来自适应评估也可能使用评论数据。评论采集本身不是任一研究方法：它负责发现汽车之家新能源汽车车系、保存完整原始口碑，并提供稳定查询与导出。实验室已说明具有相应授权协议；软件仍需限速，并在 403、429 或验证页面出现时停止。

## 决策驱动因素

- 同一份原始评论应能被两个研究方向选择，不随某个研究项目删除或改写；
- 采集任务具有浏览器依赖、长时运行、暂停和断点，与多准则项目/准则版本生命周期不同；
- 本机单用户部署应继续保持一个启动入口、一个 SQLite 文件和简单恢复方式；
- 原始对象、车系 ID/名称、来源和内容哈希必须可追溯。

## 备选方案

### 方案 A：独立平台子系统

在平台首页增加与两个研究入口平级的 `#/collection`。后端按 domain、repository、source adapter、service、API 分层；前端拥有独立 workspace 和四页工作区。采集数据作为平台级只读资产，研究处理通过稳定 ID 引用。

优势是职责和生命周期清楚，采集能力可被两个研究方向复用，仍保持单体本机部署。代价是平台出现第三套模块状态，并需维护浏览器运行依赖。

### 方案 B：放入多准则“数据中心”

入口更少，但会使评论资产从属于多准则项目，未来自适应研究要跨模块读取其内部状态，也容易把采集和 LLM 准则提取混成一个不可复用流程。

### 方案 C：仓库外独立采集工具

可隔离浏览器依赖，但用户需要单独启动、复制文件和维护数据版本，难以保证研究页面、JSONL 与 SQLite 使用同一身份和来源链。

## 决策

采用方案 A。平台模块注册表按 `collection`、`mcdm`、`adaptive` 排列；三个入口平级，不画出强制前后关系。采集服务使用单工作线程和持久化断点，Playwright 只负责动态目录和临时会话，HTTPX 负责评论分页。目标域名由服务端允许列表固定，不接受用户提供的任意网址。

`original_review` 始终保存一条汽车之家口碑的完整原始 JSON，不拆分、拼接、摘要或清洗。多准则和未来自适应系统只能读取并引用评论 ID、车系 ID、内容哈希或数据快照时间；大模型判断、人工修订、准则映射和评估结果由各研究系统拥有，不回写原始对象。

## 后果

### 正向

- 评论采集和研究处理可以独立演进、独立失败和独立恢复；
- 两个研究方向共享同一可追溯原始资产，不复制来源适配器；
- 用户能在一个网站中完成采集、查询、详情查看和 JSONL 导出；
- 限速、错误暂停和单任务约束集中在一个服务层。

### 代价与风险

- 新环境除 Python 包外还需安装锁定版本的 Chromium；
- 汽车之家页面和未文档化结构变化会使适配器暂停，需要维护固定夹具和人工冒烟；
- 进程内单线程不适合多机并发，但符合当前本机、低频和单用户范围；
- 与 SQLite 共库简化备份，也意味着未来拆分部署时需要明确迁移采集资产。

## 验证与回退

离线测试验证解析、无损存储、幂等、游标事务、状态控制、重试、API 和前端状态；联网验收只运行最多 3 车系 × 2 页。若未来采集必须独立部署，可保留 `/api/collection`、稳定标识和 JSONL 契约，将 repository/service 移至独立进程；研究模块不需要改写原始数据模型。

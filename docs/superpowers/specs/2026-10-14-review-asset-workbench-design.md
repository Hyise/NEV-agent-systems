# 评论数据工作台与可追溯资产管理设计

**日期：** 2026-10-14

**状态：** 已完成对话设计，待书面审核

**范围：** 评论采集系统、评论资产管理、人工导入、多准则研究入口

## 1. 背景与目标

当前系统已经把汽车之家车系、完整评论对象、采集任务和断点保存到 `.runtime/platform.sqlite3`，前端能够按车系分页查看评论详情和导出 JSONL。现有页面以“总览、任务、车系、评论”等技术对象组织，用户需要自行理解车系发现、评论采集、数据检查和多准则分析之间的顺序；评论资产也只有查询和导出能力，没有人工导入、管理元数据和永久删除入口。

本次改造把评论采集系统升级为“获取数据—管理数据—用于研究”的评论数据工作台，使汽车企业分析人员和研究人员能够：

1. 按引导完成车系发现和评论采集。
2. 导入单条 JSON 或批量 JSONL 评论。
3. 查询评论，维护标签、备注和分析启用状态。
4. 永久删除原始评论，同时保留最小删除审计和已有研究快照。
5. 检查可分析数据规模后进入多准则准则发现或评论标注。

成功标准是用户无需理解内部表和模块即可完成完整流程；任何管理操作都不能改写原始评论；删除不会破坏已完成研究的复核记录。

## 2. 已确认的数据口径

- 汽车之家采集和人工导入的 `original_review` 均为只读原始数据，前端和管理 API 不提供原文修改能力。
- “修改”仅指标签、备注和是否允许进入后续分析。
- 人工导入数据标记为 `manual_import`，不得伪装成汽车之家在线采集结果。
- 删除会真实移除评论资产库中的原始 JSON，不提供旧原文恢复。
- 删除审计只保留资产 ID、来源、来源评论 ID、车系、原内容哈希、删除原因和时间，不保留原文。
- 删除前已经建立的准则发现或评论标注快照和结果继续保留，并显示“源评论已删除”。
- 删除墓碑默认阻止同一汽车之家评论在后续采集中被静默写回；“允许重新采集”只解除未来采集限制，不恢复旧原文。
- 新建分析任务只读取原文仍存在且 `analysis_enabled=true` 的评论资产。

## 3. 方案选择

采用在现有评论采集系统内建设三阶段工作台的方案，不新增顶级“数据资产中心”。现有采集模块已经拥有来源适配器、SQLite 表、任务编排和评论查询边界，在该边界内扩展资产治理能避免重复存储和跨模块耦合。

不采用以下方案：

- 独立数据资产子系统：当前只有评论一种共享资产，新增顶级入口和迁移层属于过度设计。
- 只在原评论列表增加 CRUD 按钮：无法解决采集、整理和研究使用之间缺少引导的问题。

## 4. 总体架构

```text
汽车之家适配器 ─┐
                 ├─> 评论资产仓储 ─> 资产查询/元数据/删除 API ─> 评论数据工作台
人工 JSON/JSONL ─┘         │
                            ├─> 删除审计与重采墓碑
                            └─> 只读有效资产契约 ─> 多准则分析快照
```

职责边界如下：

- `backend/collection/autohome.py` 只负责读取汽车之家，不写数据库。
- `backend/collection/repository.py` 继续拥有在线采集写入和任务数据；评论资产的导入、元数据和删除操作拆入同目录的专用仓储，避免继续扩大采集任务仓储。
- 评论资产 API 属于 `/api/collection`，不进入研究项目 API。
- `backend/review_analysis/` 只读取“有效评论资产”契约，不导入汽车之家适配器，也不修改评论资产。
- 前端采集工作台创建一次采集状态、目录发现状态和资产管理状态；页面组件只消费状态和动作。

## 5. 数据模型

### 5.1 评论资产标识

现有 `reviews` 表继续保存原始评论，不建立第二份原文主表。新增：

- `asset_id TEXT`：面向 API 和前端的唯一稳定标识。
- `source_kind TEXT`：`autohome` 或 `manual_import`。

现有汽车之家记录按 `autohome:{review_id}` 确定性回填 `asset_id`。人工导入使用 `manual:{uuid}`，即使导入文件自带 `review_id` 也不会与在线来源碰撞。数据库为 `asset_id` 建唯一索引，原有 `(platform, review_id)` 主键保持兼容。

`platform` 继续表示数据提供方：在线采集保持 `autohome`，人工导入写为 `manual`；`source_kind` 表达进入系统的方式，避免以后扩展其他平台时把“平台”和“导入方式”混为一谈。人工导入时为对应车系写入 `platform='manual'` 的车系记录，资产查询和研究来源按 `series_id` 聚合不同提供方，来源筛选仍可区分两者。

汽车之家重采仍由来源写入边界处理：相同来源 ID 的动态展示字段只更新确认时间和保存对象；稳定内容变化继续写入 `review_changed` 事件。管理 API 永远不能走该写入路径。

### 5.2 管理元数据

新增 `review_asset_metadata`：

| 字段 | 规则 |
| --- | --- |
| `asset_id` | 主键，与当前评论资产一一对应 |
| `analysis_enabled` | 布尔值，默认 `true` |
| `tags_json` | 最多 20 个唯一标签，每个 1～30 字符 |
| `note` | 最多 1000 字符 |
| `revision` | 从 1 开始，修改时递增 |
| `created_at` / `updated_at` | UTC ISO 8601 |

标签、备注和分析状态与原始评论分表保存，确保管理操作不会改变 `content_hash`。删除评论时同步删除其管理元数据。

### 5.3 删除审计与墓碑

新增 `review_deletion_audits`：

| 字段 | 说明 |
| --- | --- |
| `asset_id` | 被删除资产的稳定标识 |
| `source_kind` / `platform` / `review_id` | 来源身份 |
| `series_id` / `series_name_snapshot` | 删除时车系快照 |
| `content_hash` | 删除时原内容哈希 |
| `reason` | 必填，1～500 字符 |
| `deleted_at` | 删除时间 |
| `recollection_allowed_at` | 为空时阻止同来源评论重新写入 |

该表不保存原文、来源 URL、标签或备注。在线采集保存每条评论前检查墓碑；命中且未允许重新采集时跳过，并计入任务的人工删除跳过统计。

### 5.4 分析快照引用

新建分析任务时把 `asset_id` 一并写入 `review_analysis_job_reviews`。历史行允许该字段为空，通过原有评论 ID 和内容哈希展示历史记录。分析查询通过当前资产是否存在计算 `source_deleted`，但不把评论资产设为分析结果的外键，避免删除源记录级联破坏不可变快照。

## 6. 人工导入契约

单条 JSON 和 JSONL 的每一行使用相同结构：

```json
{
  "series_id": "5769",
  "series_name": "Model Y",
  "review_id": "optional-source-id",
  "source_url": "https://example.test/review/1",
  "original_review": {
    "feeling_summary": "整体使用感受",
    "contents": [
      {"structuredname": "满意", "content": "空间充足"}
    ]
  }
}
```

- `series_id`、`series_name` 和 `original_review` 必填；`review_id`、`source_url` 可省略。
- `series_id` 保持现有数字车系口径；人工导入可建立同 ID 的人工来源车系记录。
- `source_url` 只接受 `https://` 或省略；省略时前端不显示“查看来源”。
- 必须能从 `feeling_summary` 或 `contents[].content` 确定性提取非空分析文本。
- 文件必须是 UTF-8，最大 8 MB，最多 10,000 条。
- 非对象、非法 JSON、空正文、非法 URL、字段超限和非有限数值均作为带行号的校验错误。
- 同一人工来源评论 ID或同一稳定内容哈希不重复写入。

前端在本机读取 JSON/JSONL 并转换为 JSON 数组，先调用校验接口，展示可导入、重复和错误三类结果。校验响应包含基于规范化输入和当前重复状态计算的 `validation_fingerprint`。确认导入时重新提交同一批数据及该指纹；后端重新校验并在单事务中写入所有可导入项。指纹或校验结果发生变化时返回冲突，不进行部分写入。

## 7. HTTP API

新增接口：

- `GET /api/collection/review-assets`：按关键词、车系、来源、标签和分析状态分页查询。
- `GET /api/collection/review-assets/{asset_id}`：返回完整原始对象、管理元数据、当前引用计数和删除状态。
- `POST /api/collection/review-assets/import/validate`：校验 JSON 数组形式的导入项，不写库。
- `POST /api/collection/review-assets/import`：提交已确认数据，原子导入。
- `PATCH /api/collection/review-assets/{asset_id}/metadata`：提交 `revision`、标签、备注和分析状态。
- `DELETE /api/collection/review-assets/{asset_id}`：提交删除原因、当前内容哈希和明确确认值。
- `GET /api/collection/deletions`：分页查看不含原文的删除记录。
- `POST /api/collection/deletions/{asset_id}/allow-recollection`：解除未来重采阻止。
- `PATCH /api/collection/review-assets/metadata`：批量设置分析状态或增删标签，不支持批量永久删除。
- `GET /api/collection/review-assets/summary`：返回管理和研究交接页所需的服务端统计。

现有 `/reviews` 查询和导出接口在本次迁移期保留，前端改用新接口；删除和元数据操作只提供新接口。

错误口径：

- `404`：资产不存在。
- `409`：元数据 revision 冲突、删除时哈希变化、存在活动采集任务、导入校验结果已变化。
- `410`：资产已永久删除，响应只包含最小删除审计。
- `422`：导入结构、字段、文件范围或删除确认不合法。

API 和日志不得记录完整评论正文、导入文件内容或大模型输入，只记录资产 ID、错误类型和必要统计。

## 8. 删除事务与并发规则

永久删除按以下顺序在一个数据库事务内完成：

1. 按 `asset_id` 读取当前资产和元数据。
2. 检查不存在包含该车系的可继续评论采集任务；排队、发现、采集或暂停状态均阻止删除。
3. 比较请求中的 `content_hash` 与当前值。
4. 写入不含原文的删除审计。
5. 删除管理元数据和 `reviews` 原始记录。
6. 提交事务。

前端必须要求用户填写删除原因，并输入当前评论 ID进行确认。删除成功后立即从列表移除并清空详情。数据库失败时整体回滚，前端保留用户填写内容供重试。

分析任务在创建时已经复制不可变文本，因此源评论在任务开始后被删除不会中止任务。删除不会清理分析任务、候选方案、标注结果、缓存或 token 记录。

## 9. 前端信息架构

采集系统导航改为三个任务页面：

### 9.1 获取数据

固定展示“发现车系 → 选择车系 → 采集评论”流程，根据当前状态只突出一个建议动作：

- 无目录：开始发现车系。
- 有目录无评论：选择车系并创建采集任务。
- 有暂停任务：继续或停止。
- 正在采集：查看当前车系、页码、保存数和控制操作。
- 已有评论：继续采集或进入管理数据。

目录发现、选择、任务配置和当前状态整合在同一页面；历史任务收纳在下方，不再要求用户跨多个技术页面往返。

### 9.2 管理数据

页面使用“筛选工具栏 + 数据表 + 详情抽屉”：

- 筛选车系、来源、分析状态、标签和关键词。
- 表格显示评论 ID、车系、来源、正文摘要、标签、分析状态和采集/导入时间。
- 顶部提供导入、批量分析状态和批量标签操作。
- 详情抽屉分为“原始数据、管理信息、研究引用、删除数据”。
- 原始 JSON 只读显示；管理信息使用 revision 保存；删除区使用独立危险样式和二次确认。

导入对话框按“选择文件 → 校验预览 → 确认写入”三步进行，并保留错误行号和重复原因。

### 9.3 用于研究

展示可分析评论总数、禁用数、来源分布、各车系数量和不可用原因。提供“进入准则发现”和“进入评论标注”两个入口；跳转只携带页面意图，不自动创建任务，最终来源范围仍由多准则系统中的用户确认。自适应评估仍保持规划状态。

### 9.4 引导与视觉规则

进入采集系统后直接显示紧凑三阶段进度栏和下一步建议，不保留重复数字总览页。继续使用宋体、白底表格和克制青色状态提示，不增加渐变、大面积卡片或装饰性 AI 元素。

移动端把详情改为全屏抽屉；数据表仅自身横向滚动。对话框和抽屉支持 Escape、初始焦点和关闭后焦点恢复；所有控件有可访问名称和可见焦点。

## 10. 前端状态边界

- `workspace.ts` 继续拥有采集任务、页面导航和全局错误。
- `catalogFlow.ts` 继续独占目录发现、搜索、选择和任务创建。
- 新增 `assetWorkspace.ts`，独占评论资产筛选、分页、详情、元数据 revision、批量操作、导入预览和删除状态；由 `CollectionWorkbench.vue` 创建并提供一次。
- `api.ts` 统一声明评论资产请求和响应类型，不在组件中直接调用 `fetch`。
- `AcquireView.vue`、`AssetsView.vue`、`ResearchHandoffView.vue` 只负责各自页面展示；导入向导和资产详情抽屉按独立生命周期拆为组件。
- 所有查询使用请求代际标识，过期响应不能覆盖新筛选或已关闭详情。

## 11. 迁移策略

迁移在仓储初始化时幂等执行，并包在数据库事务中：

1. 为 `reviews` 增加资产标识和来源字段。
2. 创建唯一索引、管理元数据表和删除审计表。
3. 为现有汽车之家评论回填确定性资产 ID、`autohome` 来源和默认启用元数据。
4. 为分析任务评论增加可空 `source_asset_id`，可确定映射的历史记录进行回填。

迁移不改变现有原始 JSON、内容哈希、车系、采集时间或分析结果。任一步失败均回滚；启动错误提示用户先备份 `.runtime/platform.sqlite3`，不得在半迁移状态继续运行。

## 12. 测试与验收

### 12.1 后端自动化

- 现有数据迁移和重复初始化。
- 汽车之家资产 ID稳定性、人工导入 ID隔离。
- 导入校验、行号、重复检测、大小/数量限制和事务回滚。
- 原始数据无管理更新路径。
- 标签、备注、分析状态和 revision 冲突。
- 删除审计不含原文、墓碑跳过重采、允许未来重新采集。
- 删除时活动任务和内容哈希冲突。
- 删除后分析快照、候选和标注结果仍存在且显示 `source_deleted`。
- 新分析任务只读取有效且启用的资产。
- 现有采集、导出、准则发现和评论标注回归测试继续通过。

### 12.2 前端自动化

- 三阶段引导状态和下一步建议。
- 资产筛选、分页和过期响应隔离。
- 导入校验预览、重复/错误展示和确认写入。
- 元数据保存、revision 冲突和批量操作。
- 详情抽屉、只读原文、引用状态和永久删除确认。
- `404`、`409`、`410`、`422` 和网络失败恢复。

### 12.3 真实流程验收

- 桌面和 390px 窄屏完成“发现或导入 → 管理 → 进入多准则系统”。
- 使用小型 JSON/JSONL 夹具验证导入，不写入敏感数据。
- 使用临时数据库验证永久删除和历史分析保留，不对正式本机评论做删除验收。
- 联网采集仍遵循最多 3 个车系、每车系最多 2 页的人工冒烟边界。
- 执行后端全量测试、前端单测、设计检查、格式检查、类型检查和生产构建。

## 13. 非目标

- 不提供原始评论正文编辑或删除恢复。
- 不提供批量永久删除。
- 不在本阶段建立通用文件资产中心。
- 不自动创建准则发现、评论标注或自适应评估任务。
- 不改变汽车之家访问频率、授权边界或反验证策略。
- 不自动把评论聚合为训练矩阵或重新运行研究模型。

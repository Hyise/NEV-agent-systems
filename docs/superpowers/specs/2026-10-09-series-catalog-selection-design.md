# 观衡车系发现与选择性评论采集设计规格

- 状态：已批准实施；实网目录发布验收未通过
- 日期：2026-10-09
- 适用系统：评论数据采集系统
- 核心决策：把车系目录发现与评论采集拆分为两个独立步骤
- 数据口径：按 `platform + series_id` 去重后的前 1000 个唯一车系
- 关联规格：本规格覆盖《2026-10-08 评论数据采集系统设计规格》中“任务内发现前 500 个车系”的相关条款，其余条款继续有效

## 1. 背景与目标

现有评论采集任务在启动后自行发现车系，用户在任务创建前无法查看目录，也不能选择具体车系。这使“发现有哪些车系”和“采集哪些车系”耦合在同一条长任务中，不利于研究人员控制数据范围，也会造成重复发现。

本次改造将工作流拆成两步：

1. 独立发现并缓存汽车之家新能源入口中按出现顺序排列的前 1000 个唯一车系。
2. 用户从当前有效目录中搜索、选择车系，再创建评论采集任务。

成功标准是：用户可以先看到完整的可选车系目录，再明确选择采集对象；目录刷新不会破坏上一次可用数据，也不会改变已经创建的评论任务。

## 2. 已确认的数据口径

“前 1000 个车型”在系统界面和实现中统一解释为“按发现顺序得到的前 1000 个唯一车系”。

- 去重键为 `platform + series_id`，其中 `platform` 固定为 `autohome`。
- 同一车系的不同年款、改款和配置不重复计数。
- 发现过程应持续读取数据，直到获得 1000 个唯一 `series_id`，或数据源明确没有更多车系。
- 每个可选项必须同时具有 `series_id` 和 `series_name`。
- 缺少任一必填字段的条目不得进入有效目录，但应计入解析异常统计。
- 评论中的年款、配置和 `spec_id` 等原始字段继续保留，不因车系级去重而删除。

目录数量不足 1000 不等于任务失败。当数据源正常耗尽时，发现任务以“完成但不足 1000”结束，并展示实际数量和说明。

## 3. 范围

### 3.1 包含

- 独立的异步车系发现任务。
- 当前有效车系目录及其缓存元数据。
- 发现进度、取消、错误记录和历史运行摘要。
- 车系目录搜索、分页、勾选和批量选择。
- 基于用户选择创建评论采集任务。
- 在任务创建时保存不可变的车系快照。
- 发现任务与评论采集任务之间的外部访问互斥。
- 对已有数据库进行非破坏式结构升级。

### 3.2 不包含

- 不在本阶段增加品牌、价格、能源类型等高级筛选条件；首版仅按车系名称和 `series_id` 搜索。
- 不定时自动访问汽车之家；目录更新由用户主动启动。
- 不建立分布式队列、Redis 或多机采集。
- 不改变完整原始评论对象的保存口径。
- 不在测试或验收中执行 1000 个车系的完整评论采集。
- 不自动删除旧评论、历史任务或导出文件。

## 4. 方案选择

采用“独立异步目录任务”方案：车系发现拥有自己的服务、持久化状态和 API，评论任务只消费已经发布的目录快照。

未采用以下方案：

- **打开弹窗时同步发现**：实现简单，但一次扫描可能持续较久，容易造成 HTTP 超时，页面关闭后也难以恢复进度。
- **先创建评论草稿任务再发现**：能够复用部分任务代码，但会让目录状态、用户选择和评论任务状态相互依赖，后续维护成本更高。

异步目录任务可以独立显示进度、失败和取消状态，并通过临时批次实现原子发布，是当前本机单用户系统中复杂度与可靠性的平衡点。

## 5. 总体架构

新增组件及其职责：

- `SeriesCatalogService`：启动、取消和查询发现任务；组织去重、进度更新和目录发布。
- `SeriesCatalogRepository`：读写目录批次、当前目录和发现运行记录。
- `AutohomeSeriesDiscovery`：遍历汽车之家新能源车型入口并返回标准化车系记录；不写数据库，也不决定任务状态。
- `ExternalAccessCoordinator`：为车系发现和评论采集提供同一把进程级访问锁。
- `CollectionService`：校验选中车系、生成任务快照，并按快照采集评论；不再负责车系目录发现。

依赖方向为：

```text
Catalog API → SeriesCatalogService → SeriesCatalogRepository
                         ├──────────→ AutohomeSeriesDiscovery
                         └──────────→ ExternalAccessCoordinator

Collection API → CollectionService → CollectionRepository
                         ├──────────→ 当前目录（只读校验）
                         ├──────────→ 评论适配器
                         └──────────→ ExternalAccessCoordinator
```

车型发现和评论采集不能同时访问汽车之家。互斥只限制外部采集操作，不影响用户浏览缓存目录、历史任务和已保存评论。

## 6. 两阶段业务流程

### 6.1 第一步：发现车系

```text
用户启动发现
  ↓
创建 catalog run 并获取外部访问锁
  ↓
逐页/逐批读取新能源汽车车型入口
  ↓
按 series_id 去重并写入临时目录批次
  ↓
达到 1000 个唯一车系或数据源耗尽
  ↓
同一事务中发布新批次并更新当前目录指针
  ↓
释放外部访问锁
```

已有有效目录时，重新发现不得预先清空目录。只有新批次成功完成后才替换当前目录；失败或取消时删除未发布的临时记录，继续提供旧目录。

### 6.2 第二步：选择车系并采集

```text
读取当前有效目录
  ↓
搜索并勾选车系
  ↓
选择功能验证或正式采集模式
  ↓
后端重新校验车系与数量限制
  ↓
在事务中创建任务和不可变车系快照
  ↓
获取外部访问锁并按快照采集评论
```

评论任务开始后不再读取可变目录。即使用户随后刷新目录，已有任务仍使用创建时保存的名称、链接、发现顺序和 `series_id`。

## 7. 运行模式与选择规则

| 模式 | 可选车系数 | 每车系页数 | 用途 |
| --- | ---: | ---: | --- |
| 功能验证 | 1～3 | 固定最多 2 页 | 开发、演示、联网冒烟验证 |
| 正式采集 | 1～1000 | 不限制，采集至可靠终止条件 | 正式研究数据采集 |

- 两种模式都必须由用户选择具体车系，不再隐式使用“目录前 N 个”。
- 页面初次进入不默认勾选任何车系，避免误启动大范围任务。
- 切换到功能验证模式时，如果已选择超过 3 个车系，应保留列表选择状态但阻止提交，并提示用户缩减到 3 个以内。
- 创建正式任务前继续显示二次确认，至少列出模式、选中数量、页数规则和请求间隔。
- 后端是最终校验边界；不能只依赖前端限制。

## 8. 数据模型

### 8.1 `series_catalog_runs`

记录每次发现运行：

- `id`
- `status`：`queued`、`discovering`、`publishing`、`completed`、`completed_short`、`cancelling`、`cancelled`、`failed`
- `target_unique_series`，本阶段固定为 1000
- `scanned_count`
- `unique_count`
- `skipped_count`
- `current_page`
- `batch_id`
- `error_code`、`error_message`
- `created_at`、`started_at`、`finished_at`、`updated_at`

同一时刻最多有一个非终态的发现运行。

### 8.2 `series_catalog_entries`

保存目录批次中的车系：

- `batch_id`
- `platform`
- `series_id`
- `series_name`
- `series_url`
- `review_url`
- `discovery_rank`
- `discovered_at`

唯一约束为 `batch_id + platform + series_id`。`discovery_rank` 按首次出现顺序确定，重复项不得改变已确定的顺序。

### 8.3 `series_catalog_state`

保存单行目录状态：

- `active_batch_id`
- `series_count`
- `published_at`
- `source_url`
- `source_exhausted`

发布时在同一事务中更新活动批次指针和摘要。保留最近 3 个成功批次用于诊断；更早的成功批次在确认未被任务快照引用后清理。前端只能读取 `active_batch_id` 指向的当前目录。

### 8.4 `collection_job_series`

保存评论任务的不可变车系清单：

- `job_id`
- `platform`
- `series_id`
- `series_name_snapshot`
- `series_url_snapshot`
- `review_url_snapshot`
- `catalog_batch_id`
- `catalog_rank`
- `selection_order`

唯一约束为 `job_id + platform + series_id`。任务及其清单必须在同一事务中创建，禁止只创建空任务。

现有 `vehicle_series` 继续作为已经进入采集资产域的车系表，不替代“当前可选目录”。已有数据不迁入新目录，避免把少量历史采集车系误报为完整发现结果。

## 9. API 契约

所有路径继续使用 `/api/collection` 前缀。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/catalog` | 分页读取当前目录，支持 `query`、`page`、`page_size` |
| `GET` | `/catalog/selection` | 返回当前查询条件命中的全部车系 ID，用于“全选当前筛选结果” |
| `GET` | `/catalog/status` | 返回当前目录摘要和活动发现任务 |
| `POST` | `/catalog/discover` | 启动车系发现，目标固定为 1000 个唯一车系 |
| `POST` | `/catalog/discover/{run_id}/cancel` | 请求取消指定发现任务 |
| `GET` | `/catalog/discover/{run_id}` | 查询发现进度和错误摘要 |
| `POST` | `/jobs` | 使用 `selected_series_ids` 创建并启动评论任务 |

`GET /catalog` 的结果必须包含：`series_id`、`series_name`、`series_url`、`review_url`、`discovery_rank`、`batch_id` 和 `published_at`。

`POST /jobs` 请求增加：

```json
{
  "mode": "verification",
  "selected_series_ids": ["8627", "8584"]
}
```

后端根据模式推导页数规则，不接受前端扩大限制。以下情况返回：

- 目录尚未建立：`409`。
- 发现或其他评论采集正在占用外部访问锁：`409`。
- 选择为空、超过模式上限或包含重复 ID：`422`。
- 所选 ID 不属于当前活动目录：`422`，并返回无效 ID 列表。
- 资源不存在：`404`。

目录搜索采用服务端分页；`query` 对车系名称和 `series_id` 做包含匹配。`GET /catalog/selection` 使用同一查询规则，并只返回当前活动批次中按 `discovery_rank` 排列的 ID。首版最多 1000 条，不引入全文检索引擎。

## 10. 页面设计

评论采集页面的新建区域改成明确的两步工作流。

### 10.1 步骤一“发现车系”

显示：

- 当前有效目录数量，例如“已发现 986 / 1000 个唯一车系”。
- 最近发布时间、数据来源和“数据源已耗尽”提示。
- “开始发现”或“重新发现”主按钮。
- 发现中的当前页、已扫描条目数、唯一车系数和跳过数。
- 取消操作、错误摘要和运行结果。
- 有可用目录时的“选择车系并采集”入口。

刷新期间继续展示旧目录，并标注“正在生成新目录”；不得用空白状态覆盖旧目录。

### 10.2 步骤二“选择车系并采集”

显示：

- 搜索框，可按车系名称或 ID 搜索。
- 带复选框的车系列表，至少显示名称、ID、发现顺序和口碑入口是否可用。
- “全选当前筛选结果”“清空已选”和已选数量。
- 模式选择、规则说明和提交前确认摘要。
- 返回第一步查看或刷新目录的入口。

“全选当前筛选结果”选择所有符合当前查询条件的车系，而不仅是当前分页。前端调用 `GET /catalog/selection` 取得活动目录中符合条件的全部 ID，不依赖只加载一页后在本地猜测。

目录刷新成功后，如果页面仍停留在第二步，应重新校验选择；已经从新目录消失的未提交选项要明确提示并从可提交集合中移除。

已有任务进度、控制、日志和结果查看区域保留在新建区域下方，视觉上与两步创建流程分开。

## 11. 状态、并发和恢复

- 车系发现使用后台执行器，HTTP 请求只负责启动，不等待完整扫描结束。
- 进程重启时，处于 `queued`、`discovering`、`publishing` 或 `cancelling` 的运行标记为失败中断；临时批次不得发布。
- 当前有效目录由已提交的 `active_batch_id` 决定，因此进程中断不会产生半成品目录。
- 发现和评论采集共享单一外部访问协调器。无法取得锁时不排队隐式等待，而是返回明确的占用状态。
- 浏览目录、查看任务、查看评论和导出不占用外部访问锁。
- 评论任务原有暂停、继续、停止和断点续采行为保持不变；继续时仍使用其任务快照。

## 12. 错误处理

- 临时网络错误沿用受控重试和退避策略。
- 收到 `403`、`429` 或验证页面时，发现任务失败并保留旧目录；不得尝试绕过验证。
- HTML 或结构化数据契约漂移时记录明确错误，不通过模糊选择器猜测车系。
- 单个条目缺少必填字段时跳过并累计。扫描至少 100 个原始条目后，如果必填字段缺失率超过 5%，整次发现失败；非空来源页解析出 0 个有效条目时立即按结构漂移失败，避免发布明显残缺的目录。
- 数据源正常耗尽且已发现数量不足 1000 时使用 `completed_short`，不是 `failed`。
- 用户取消时采用协作式取消：当前请求结束后、下一次请求前生效。
- 发布事务失败时活动目录指针保持不变，并把本次运行标记为失败。
- 评论任务创建时，如果目录在用户浏览后发生变化，以提交瞬间的活动目录为准并返回失效 ID。

## 13. 数据库升级与兼容性

- 新表通过现有启动迁移机制创建，不重建或清空旧表。
- 现有 `collection_jobs`、`vehicle_series`、`reviews` 和事件记录原样保留。
- 旧任务仍可查看、继续和导出；旧任务没有 `collection_job_series` 时继续读取现有 `collection_jobs.series_manifest` JSON。该字段仅作为旧任务兼容路径，新任务不再写入。
- 新任务必须使用 `collection_job_series`，不得退回任务内自动发现。
- 首次升级后目录为空，界面引导用户执行第一次发现。
- API 变更需要同步前端调用和项目数据契约文档，不长期保留两个含义不同的任务创建方式。

## 14. 测试策略

### 14.1 后端单元与集成测试

- 用固定 HTML/JSON 夹具测试车系解析，不依赖在线网站。
- 测试不同年款和配置共享 `series_id` 时只保留一个车系。
- 测试扫描超过 1000 个原始条目，直到得到 1000 个唯一车系。
- 测试数据源不足 1000 时产生 `completed_short`。
- 测试失败、取消、进程中断和发布事务异常时旧目录保持可用。
- 测试活动目录的原子切换和分页搜索。
- 测试发现与评论采集互斥，但只读操作不受影响。
- 测试验证模式 1～3 个和正式模式 1～1000 个的边界。
- 测试空选择、重复 ID、失效 ID和模式越界。
- 测试任务与 `collection_job_series` 在同一事务中创建。
- 测试目录刷新后已创建任务的快照不变。
- 测试旧任务兼容读取和现有完整评论内容不回退。

### 14.2 前端测试

- 测试空目录、可用目录、刷新中、完成不足、失败和取消状态。
- 测试搜索、单选、全选当前筛选结果和清空。
- 测试两种模式的选择数量约束和二次确认摘要。
- 测试目录版本变化后失效选择提示。
- 测试活动发现期间禁止启动评论采集，反向亦然。
- 测试键盘操作、文字状态提示和窄屏布局。

### 14.3 验证门禁

- 运行完整后端测试、前端测试、类型检查、格式检查和生产构建。
- 人工联网冒烟只发现少量真实车系，并选择 1～3 个车系采集有限页数。
- 验证真实数据中的 `series_id`、`series_name`、口碑入口和完整评论正文。
- 不在验收中发现全部 1000 个车系并采集其全部评论。

## 15. 验收标准

1. 页面明确分为“发现车系”和“选择车系并采集”两个步骤。
2. 发现任务能异步运行、展示进度并支持取消。
3. 系统最多发布按发现顺序排列的 1000 个唯一车系。
4. 不同年款、改款和配置不会形成重复选择项。
5. 刷新失败或取消不会破坏上一次有效目录。
6. 用户可以按名称或 ID 搜索、勾选和批量选择车系。
7. 功能验证与正式采集都必须使用明确选择的车系。
8. 新评论任务保存不可变的车系快照，不受后续目录刷新影响。
9. 发现和评论采集不会并发访问汽车之家。
10. 已有评论、任务、导出及完整评论正文不被破坏。
11. 自动化测试不依赖汽车之家实时可用性。
12. README、运行须知、API 与数据契约、架构规范和验收记录与实现同步。

## 16. 实施边界与文档同步

实现阶段应按以下边界推进：

1. 先建立数据模型、仓储和迁移，再增加发现服务与互斥协调器。
2. 接着实现目录 API 和任务快照契约，删除新任务中的隐式发现路径。
3. 然后改造前端两步流程和选择交互。
4. 最后执行兼容性测试、真实小范围冒烟和文档同步。

需要同步更新：

- `AGENTS.md` 中的采集模块边界。
- `开发与架构规范.md` 中的目录服务、任务快照和互斥规则。

# 观衡评论数据采集系统设计规格

- 状态：待用户书面复核
- 日期：2026-10-08
- 决策：在平台首页新增与两个研究系统平级的“评论数据采集系统”
- 数据源：汽车之家新能源汽车公开口碑页面
- 当前阶段：完成可运行、可暂停、可续采的采集能力；不接入大模型准则提取

## 1. 背景与目标

观衡研究平台当前提供“多准则决策系统”和“自适应评估系统”两个入口。评论采集不属于其中任一研究方法，而是两个研究方向都可能使用的原始数据来源。因此，本设计把评论采集建设为第三个独立功能子系统，而不是放入多准则工作台的“数据中心”。

用户已说明实验室与汽车之家存在相应授权协议。本系统在该授权范围内，以汽车之家新能源汽车页面为入口，发现前 500 个唯一车系，并支持逐车系采集全部口碑。开发和验收期间只运行小范围功能验证，不执行完整批量任务。

系统面向汽车企业分析人员和研究人员，成功标准是：

- 用户能够从平台首页直接进入评论数据采集系统。
- 采集单位是“车系”，不同年款、改款和配置归入同一车系。
- 每个车系同时保存汽车之家 `series_id` 和车系名称。
- 每条口碑作为一个完整原始对象保存，不拆分、不拼接、不改写。
- 长时间任务支持限速、暂停、停止、失败记录和断点续采。
- 采集数据成为平台级数据资产；两个研究系统以后分别选择并处理这些数据。
- 代码按适配器、任务编排、持久化、API 和界面分层，避免采集规则渗入研究模块。

## 2. 范围

### 2.1 包含

- 在平台首页新增“评论数据采集系统”入口，与多准则和自适应评估入口平级排列。
- 新增独立路由 `/#/collection` 和独立工作区。
- 从 `https://www.autohome.com.cn/price/ev#pvareaid=3311257` 发现新能源汽车车系。
- 按页面展示顺序保存最多 500 个唯一车系。
- 按 `series_id` 分页采集车系全部口碑，跨年款、改款和配置汇总。
- 保存车系目录、完整原始评论、任务状态、断点和采集事件。
- 提供功能验证与正式采集两种运行模式。
- 提供采集总览、任务管理、车系浏览、原始评论浏览和 JSONL 导出。
- 为后续研究系统选择数据预留稳定标识和只读查询边界。

### 2.2 不包含

- 不在本阶段调用大模型 API，不提取准则，不生成摘要或情感标签。
- 不把评论拆成“满意”“不满意”等子记录，也不合并原始字段生成新文本。
- 不按年款、改款、配置建立独立车型或独立采集任务。
- 不默认导出会破坏嵌套结构的 CSV。
- 不实现自适应评估系统对评论的处理。
- 不在采集系统内建立多准则研究项目、准则版本或评估任务。
- 不尝试绕过验证码、访问限制或平台验证机制。
- 不加入云端任务队列、Redis、Celery、分布式采集或多用户并发。
- 不在自动化测试或日常验收中批量采集 500 个车系的全部评论。

## 3. 平台信息架构

平台首页采用三个平级入口：

```text
观衡研究平台
├── 评论数据采集系统（已开放）
│   ├── 总览
│   ├── 采集任务
│   ├── 车系
│   └── 原始评论
├── 多准则决策系统（已开放）
│   └── 现有研究工作台
└── 自适应评估系统（规划中）
    └── 现有规划说明页
```

三个入口在视觉和导航层级上平级，但职责不同：

- 评论采集系统只产生和管理可追溯的原始评论数据。
- 多准则系统以后自行选择评论数据并完成准则判断、模型处理和结果分析。
- 自适应评估系统以后自行选择评论数据并执行其研究流程。
- 研究系统不得直接调用汽车之家适配器；它们只能读取采集系统已保存的数据资产。

## 4. 数据口径

### 4.1 车系口径

车系的稳定标识为：

```text
platform + series_id
```

其中 `platform` 固定为 `autohome`。`series_name` 必须与 `series_id` 同时保存，用于展示、搜索、导出和研究识别。

不同年款、年度改款和配置不成为独立采集单位。汽车之家口碑返回的 `spec_id`、`spec_name`、年款等字段仍保留在原始评论对象中，但不会影响车系去重和任务调度。

如果汽车之家以后修改车系名称：

- `vehicle_series` 保存最近确认的名称。
- 已保存评论保留采集当时的 `series_name` 快照。
- 历史导出不因名称更新而失去当时语境。

### 4.2 评论口径

汽车之家返回的一条口碑对应数据库中的一条 `reviews` 记录。`original_review` 保存该口碑条目的完整原始 JSON 对象，包括其原有嵌套字段和顺序语义。

采集层不得：

- 拆分 `contents` 数组为多条评论。
- 拼接标题、总结、“满意”或“不满意”等字段。
- 清洗、改写、翻译或摘要文本。
- 删除暂时未使用的原始字段。

系统只在原始对象外增加来源、车系、采集时间和校验字段，不修改 `original_review`。

示意：

```json
{
  "platform": "autohome",
  "series_id": "5769",
  "series_name": "Model Y",
  "review_id": "汽车之家原始口碑ID",
  "source_url": "原始口碑地址",
  "collected_at": "采集时间",
  "original_review": {
    "汽车之家返回的整条口碑对象": "原样保存"
  }
}
```

评论优先使用 `platform + review_id` 去重。原始口碑 ID 缺失时，使用 `platform + series_id + canonical JSON SHA-256` 作为备用唯一键。Canonical JSON 仅用于稳定计算哈希，不替换保存的原始对象。

## 5. 采集架构

### 5.1 方案

采用已确认的混合方案：

- 浏览器自动化负责动态车系目录发现和必要的会话建立。
- 结构化分页请求负责评论采集。
- 页面解析只作为结构化接口不可用时的显式降级路径。

选择该方案的原因是：新能源汽车目录存在动态加载，而车系口碑页使用结构化分页数据。混合方案比全页面解析更节省资源，也比只依赖未文档化接口更能适应会话或页面变化。

任何降级都必须记录采集方式。适配器发现返回结构变化时应失败并暂停，而不是猜测字段或静默丢弃数据。

### 5.2 两阶段流程

```text
创建任务
  ↓
发现车系：动态加载新能源汽车目录
  ↓
按出现顺序用 series_id 去重并保存前 N 个车系
  ↓
逐车系分页采集：yearid=0，不按年款筛选
  ↓
每成功保存一页即提交数据并更新断点
  ↓
完成、部分失败、暂停或停止
```

车系发现至少保存：`series_id`、`series_name`、车系页面地址、口碑页面地址、发现顺序和发现时间。

评论分页终止条件按以下顺序判断：

1. 已达到验证模式的每车系页数上限；或
2. 已达到响应声明的评论总数；或
3. 返回空列表；或
4. 返回页与上一页具有相同评论 ID 集合，此时记录异常并停止该车系，防止死循环。

正式模式的每车系页数上限为空，表示采集至可靠终止条件。

### 5.3 运行模式

| 模式 | 默认车系数 | 每车系页数 | 用途 |
| --- | ---: | ---: | --- |
| 功能验证 | 3 | 2 | 开发、演示和验收 |
| 正式采集 | 500 | 不限制 | 经用户确认后的研究数据采集 |

功能验证模式允许在前端降低车系数或页数，但不能超过正式范围。正式模式启动前必须显示采集范围和限速配置并要求二次确认。

正式模式中的“前 500 个车系”指目录页按发现顺序得到的前 500 个唯一 `series_id`，不是前 500 个年款或配置。

## 6. 任务调度与状态

本机版采用单工作线程。任一时刻最多有一个正在发现、采集或恢复中的任务；历史任务数量不受此规则限制。已有活动任务时再次启动返回 `409`。

任务状态：

```text
queued → discovering → collecting → completed
                  ├──→ paused → collecting
                  ├──→ stopped
                  └──→ partial_failed
```

- `paused`：保留断点，用户可以继续。
- `stopped`：结束本次任务并保留已有数据，不允许继续；需要新建任务重新检查。
- `partial_failed`：任务遍历结束，但一个或多个车系失败；成功数据仍可用。
- 配置无效或目录完全无法解析时直接返回错误，不创建伪成功任务。

任务游标至少包含：

- 当前车系发现数量。
- 当前车系序号、`series_id` 和 `series_name`。
- 当前分页页码。
- 已保存、重复、失败和跳过数量。
- 最后成功时间与最后错误摘要。

每页评论和游标在同一事务中提交。进程退出可能重复请求最后一页，但幂等去重保证不会重复保存。

## 7. 限速、重试与停止

默认策略：

- 单请求串行执行。
- 分页请求之间随机等待 2～4 秒。
- 完成一个车系后随机等待 5～10 秒。
- 请求超时 20 秒。
- 临时网络错误最多重试 3 次，等待 5、15、45 秒。
- 服务端强制最小请求间隔，前端不能配置为零。
- 收到 `403`、`429` 或检测到验证页面时立即暂停任务，不继续重试和绕过。

暂停和停止采用协作式取消：当前 HTTP 请求结束后、下一次请求发出前生效。界面应显示“正在暂停”或“正在停止”，不能在请求仍执行时提前显示最终状态。

连续请求失败达到阈值时自动暂停整个任务。单个车系在重试后仍失败则记录事件并进入下一车系；任务结束时标记为 `partial_failed`。

## 8. 后端模块边界

目标结构：

```text
backend/
├── app.py                         应用装配，挂载 collection router
└── collection/
    ├── api.py                     HTTP 路由与请求编排
    ├── domain.py                  配置、状态机、校验和纯业务规则
    ├── service.py                 任务编排、限速、重试和断点
    ├── repository.py              SQLite 持久化
    └── autohome.py                车系目录与评论页适配器
```

依赖方向：

```text
API → service → domain
        ├────→ repository
        └────→ autohome adapter
```

- `domain.py` 不依赖 FastAPI、浏览器自动化或 SQLite。
- `autohome.py` 不写数据库，不决定任务状态。
- `repository.py` 不发起网络请求。
- `service.py` 通过适配器和仓储接口编排流程，不解析 HTML 选择器。
- 多准则和自适应模块不得导入 `autohome.py` 或 `service.py`。
- 新模块不继续膨胀现有通用 `backend/store.py` 和 `backend/domain.py`。

## 9. 持久化模型

### 9.1 `collection_jobs`

主要字段：

- `id`
- `mode`：`verification` 或 `production`
- `source_url`
- `max_series`
- `max_pages_per_series`，正式模式为空
- `request_delay_min_seconds`、`request_delay_max_seconds`
- `series_delay_min_seconds`、`series_delay_max_seconds`
- `status`
- 当前游标及统计数量
- `created_at`、`started_at`、`finished_at`、`updated_at`

任务配置在启动后冻结。继续任务沿用原配置，不允许在断点中途修改范围或限速。

### 9.2 `vehicle_series`

主要字段：

- `platform`
- `series_id`
- `series_name`
- `series_url`
- `review_url`
- `discovery_rank`
- `first_discovered_at`
- `last_confirmed_at`

唯一约束为 `platform + series_id`。相同车系在不同任务中再次发现时更新最后确认时间和当前名称，不创建重复车系。

### 9.3 `reviews`

主要字段：

- `platform`
- `review_id` 或备用 ID
- `series_id`
- `series_name_snapshot`
- `source_url`
- `original_review_json`
- `content_hash`
- `first_collected_at`
- `last_confirmed_at`

`original_review_json` 必须能够反序列化回采集时的完整评论对象。普通重复采集只更新 `last_confirmed_at`；同一 `review_id` 的内容哈希变化时，用新原始对象更新当前记录并写入 `collection_events`，保留变更证据。

### 9.4 `collection_events`

保存任务 ID、可选车系 ID、事件类型、错误类别、简短消息、可重试标记和发生时间。不得保存访问凭据、Cookie 或完整响应头。

## 10. API 契约

所有路径以 `/api/collection` 开头：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/overview` | 数据规模、活动任务和待处理异常 |
| `GET` | `/jobs` | 分页查询任务 |
| `POST` | `/jobs` | 创建并启动验证或正式任务 |
| `GET` | `/jobs/{id}` | 任务配置、游标、统计和近期事件 |
| `POST` | `/jobs/{id}/pause` | 请求暂停活动任务 |
| `POST` | `/jobs/{id}/resume` | 从持久化断点继续暂停任务 |
| `POST` | `/jobs/{id}/stop` | 请求停止并保留已有数据 |
| `GET` | `/series` | 按名称、ID、任务状态分页查询车系 |
| `GET` | `/reviews` | 按车系、时间和评论 ID 分页查询摘要 |
| `GET` | `/reviews/{id}` | 获取单条完整原始评论对象 |
| `GET` | `/export` | 按车系导出 JSONL |

状态不允许时返回 `409`，参数不合法返回 `422`，资源不存在返回 `404`，采集源结构不符合预期返回可追踪的任务事件而不是伪造数据。

`GET /reviews` 默认不在列表中返回所有大型原始 JSON，只返回车系、评论 ID、原始发布时间等索引信息；打开详情时再请求完整对象。

JSONL 每行是一条自包含记录，至少包含 `platform`、`series_id`、`series_name`、`review_id`、来源和完整 `original_review`。导出不生成合并评论文本。

## 11. 前端工作区

### 11.1 平台入口

平台模块注册表新增：

- 名称：评论数据采集系统
- 状态：已开放
- 路由：`/#/collection`
- 操作：进入采集系统
- 简介：发现汽车之家车系，采集并保存完整原始口碑

三个子系统使用平级卡片或条目排列。入口不绘制评论采集向两个研究系统的强制流程箭头，避免造成只有先完成采集才能进入研究系统的误解。

### 11.2 工作区页面

保留四个简单页面：

1. **总览**：数据规模、当前任务、异常摘要和最近活动。
2. **采集任务**：新建任务、查看进度、暂停、继续、停止和查看事件。
3. **车系**：按名称或 `series_id` 搜索，查看发现顺序、评论数量和最近确认时间。
4. **原始评论**：按车系查询列表、打开完整 JSON，并导出 JSONL。

工作区不显示多准则项目、准则版本或观察月份。侧栏只显示“总览、采集任务、车系、原始评论”，不再增加导航分组标题。

### 11.3 简化原则

- 页面顶部只显示当前页标题、单句说明和一个主要操作。
- 任务页用一行文字展示车系数、评论数和来源，不使用四张统计卡。
- 同时只有一个突出的活动任务进度区域。
- 历史任务使用普通表格，不使用卡片墙。
- 不重复展示数据口径；详细规则放在新建任务确认和帮助文档中。
- 使用全站宋体回退链；减少圆角、阴影、徽章和装饰色。
- 状态除颜色外必须有文字；暂停、停止和正式采集确认支持键盘操作。

## 12. 与研究系统的数据边界

本阶段只建立稳定的数据资产标识，不实现研究处理界面。未来的连接方式是：

```text
采集系统中的车系/评论数据集
        ↓ 只读选择
多准则项目自己的处理记录

采集系统中的车系/评论数据集
        ↓ 只读选择
自适应项目自己的处理记录
```

研究系统保存所选择评论的 ID、车系 ID、数据快照时间或内容哈希，不修改采集系统原始评论。大模型输出、准则判断、人工修订和评估结果均属于研究系统，不回写 `original_review`。

## 13. 安全与运行约束

- 本机服务继续只监听 `127.0.0.1`，不得直接暴露公网。
- 采集入口和请求域名使用服务器端允许列表；API 不接受任意目标网址。
- 日志和数据库不保存授权协议内容、Cookie、令牌或浏览器凭据。
- 授权协议的有效范围和期限由实验室负责确认；系统文档把有效授权列为正式采集前提。
- 不把运行数据库、采集结果、JSONL 导出或浏览器会话文件提交 Git。
- 正式采集结果默认保存在现有运行数据目录下，并遵守项目 `.gitignore`。
- 启动脚本应同时启动现有网站和采集任务恢复检查，但不会未经用户操作自动开始正式采集。

## 14. 测试策略

### 14.1 自动化测试

- 用固定 HTML/JSON 夹具测试车系目录和评论响应解析，不在测试中访问真实网站。
- 测试同一 `series_id` 的不同年款和配置只形成一个车系。
- 测试 `series_id` 与 `series_name` 始终同时存在。
- 测试原始评论对象保存后可无损反序列化。
- 测试重复页、重复评论和内容更新的幂等行为。
- 用假时钟和假 HTTP 客户端测试限速、退避和协作式暂停。
- 测试每页事务、崩溃后断点恢复和单活动任务约束。
- 测试所有状态迁移及非法操作的 `409`。
- 测试 JSONL 每行包含完整评论和车系名称。
- 测试平台第三入口、路由回退、四页导航和窄屏无整体横向滚动。

### 14.2 人工联网冒烟验证

人工验证默认使用功能验证模式，最多 3 个车系、每车系 2 页。检查：

- 能从新能源汽车页面发现真实车系。
- 能保存真实 `series_id` 和对应车系名称。
- 能取得至少一个车系的多页评论。
- 页面能够预览完整原始对象。
- 暂停、继续和重复执行不产生重复评论。
- 浏览器控制台和后端日志没有未处理异常。

人工联网验证失败不能通过扩大重试频率解决。应先检查授权环境、页面结构、接口返回和适配器契约。

## 15. 验收标准

本阶段完成需要同时满足：

1. 平台首页出现三个平级子系统入口，评论采集可以独立进入和返回。
2. 采集工作区采用已确认的简化四页结构。
3. 功能验证模式能发现并保存多个唯一车系。
4. 每个车系包含正确的 `series_id` 和 `series_name`。
5. 不同年款、改款和配置不会拆成多个车系任务。
6. 至少一个真实车系能够完成多页评论采集。
7. 一条口碑作为一个完整原始 JSON 对象保存，不拆分、不拼接。
8. 限速、三次退避重试、暂停、停止和断点续采按设计工作。
9. 重复采集不会新增重复评论。
10. 用户能按车系查询评论并导出自包含 JSONL。
11. 自动化测试不依赖汽车之家在线可用性。
12. README、运行须知、API 契约、系统设计和测试文档与实现一致。
13. 不把采集数据、运行数据库、凭据或浏览器会话提交 Git。
14. 具备发现前 500 个唯一车系并逐车系采集全部评论的正式模式，但验收不要求实际跑完整批量。

## 16. 风险与已接受取舍

- 汽车之家页面和未文档化数据结构可能变化。通过独立适配器、固定夹具、结构校验和明确暂停降低维护影响，但不能消除变化风险。
- 单工作线程牺牲批量速度，换取更易控制的访问频率、状态一致性和本机运行简单性；当前阶段接受该取舍。
- JSONL 不如 CSV 便于直接打开，但能够无损保存嵌套原始对象；本阶段优先研究可追溯性。
- 评论表保留当前原始对象而不建设完整版本历史；当同一评论内容变化时通过事件记录变更事实。若研究以后需要逐版本复现，再单独设计评论版本表。
- 平台首页将三个系统平级展示，而不是强调采集系统是强制上游，以保证已有研究归档仍可直接进入和复核。
- 正式采集依赖实验室授权持续有效。软件实现限速和错误停止，但不替代协议管理。

# 观衡大模型准则发现与评论级语义标注设计规格

- 状态：待实施
- 日期：2026-10-10
- 适用系统：多准则决策系统
- 模型：DeepSeek-V4.1-Flash，API 标识 `deepseek-flash`
- 核心决策：先审核并冻结准则体系，再在封闭准则体系内逐条标注完整评论
- 研究来源：提示词任务结构参考师姐代码中的 `criterion_extraction.txt`、`review_annotation.txt`、`criterion_extractor.py`、`criterion_merger.py` 和 `review_annotator.py`

## 1. 背景与目标

当前平台已经能采集并保存汽车之家完整原始口碑，也能人工维护准则草稿，但两者之间没有语义处理流程。师姐代码包含“从评论发现准则”和“按准则标注评论”两类大模型任务；现有脚本面向离线 CSV，缺少网页任务状态、严格结果校验、失败恢复、版本绑定和可审计持久化。

本次建设的主要目标不是单独生成一张准则表，而是建立以下闭环：

1. 从用户选择的已采集评论中发现准则候选方案。
2. 由研究人员审核、修改并冻结准则版本。
3. 使用冻结版本逐条处理完整评论，提取评论涉及的全部准则及其有序评价等级。
4. 保存原文证据、简短判定依据、模型信息和版本信息，使每条结果可查询、可重试、可复核。

成功标准是：同一条评论的标注能够明确追溯到评论内容哈希、冻结准则版本、模型标识和 Prompt 版本；模型输出不属于冻结体系的准则或等级时不得落库为成功结果。

## 2. 已确认的研究口径

### 2.1 两类任务

- **准则发现**：从评论样本中提取线索并全局归并，形成待审核准则方案。
- **评论标注**：针对一个已经冻结的准则版本，逐条识别评论涉及的准则、等级和原文证据。

“准则提取”在界面和 API 中不得同时指代这两类不同任务，避免把“发现评价体系”与“给评论贴标签”混为一谈。

### 2.2 封闭准则体系

评论标注严格限制在任务绑定的冻结准则版本内：

- 模型不得临时创建新准则或新等级。
- 未匹配到冻结准则的原文放入 `unmatched_evidence`，作为“其他准则/待补充线索”。
- `unmatched_evidence` 不自动改变当前准则版本，也不自动迁移到后续版本。
- 如果研究人员希望吸收新线索，应派生新的准则草稿，审核后形成新版本，再创建新的标注任务。

### 2.3 评论完整性

- 来源仍是采集子系统保存的完整 `original_review`，不改写、不拆分、不覆盖原始对象。
- 分析输入由确定性转换器从 `feeling_summary` 和按原顺序保存的 `contents[].structuredname/content` 中提取文本；相同内容只去除完全重复项，不做摘要或语义改写。
- 一条汽车之家口碑始终作为一个分析单元。系统可以在 Prompt 中保留原分区标题帮助理解，但不会把分区存成多条独立评论。
- 模型返回的每段 `evidence` 必须能在该分析输入中找到完全一致的原文子串，否则结果无效。

## 3. 范围

### 3.1 本阶段包含

- 多准则工作台中的“评论语义分析”页面。
- 从已采集车系中选择评论来源。
- 可复现的分层样本选择、分批线索提取和全局准则归并。
- 准则候选方案的人工审核、编辑和写入当前自定义项目草稿。
- 冻结准则版本下的逐评论异步标注任务。
- 任务暂停、继续、取消、失败重试和应用重启恢复。
- 评论级标注查询、筛选、详情和基础统计。
- DeepSeek API 配置、结构化输出校验、用量记录和去重缓存。
- 设计、运行、API、架构和验收文档同步。

### 3.2 本阶段不包含

- 不自动冻结大模型生成的准则方案。
- 不允许大模型直接覆盖预置研究归档或已冻结版本。
- 不在本阶段训练 BEAST、重新生成销量预测或宣称复现论文结果。
- 不自动把评论标注聚合为训练用月度概率矩阵；本阶段只提供评论级结果和基础计数，概率矩阵另行设计。
- 不增加云端任务队列、Redis、多机并发或用户权限系统。
- 不把 API Key、完整 Prompt、完整评论或模型响应正文写入普通服务日志。
- 自动化测试不访问 DeepSeek 或汽车之家真实接口。

## 4. 方案选择

采用“准则发现任务 + 人工冻结 + 评论标注任务”的双任务方案。

未采用以下方案：

- **一键发现并立即全量标注**：步骤少，但未经人工核验的体系会直接影响全部结果，难以解释版本差异。
- **只用预置十项准则标注**：开发量较小，但不能满足从新评论发现准则的研究目标；现有预置版本的 `L0...L(n-1)` 与自然语言标签还存在已记录的不一致。
- **每条评论开放生成新准则**：表面灵活，但跨评论名称和等级无法稳定对齐，不能形成可复现的多准则数据。

双任务方案使准则体系成为明确的版本边界，也使高成本的逐评论调用可以暂停、重试和复用。

## 5. 总体架构

后端新增 `backend/review_analysis/`，职责按边界拆分：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| `domain.py` | 任务状态、准则方案、标注结果和严格校验 | HTTP、SQLite、网络请求 |
| `prompts/` | 版本化准则发现与评论标注模板 | 运行时密钥、数据库读写 |
| `deepseek.py` | DeepSeek Chat Completions 请求、错误归类和用量解码 | 业务状态、评论选择 |
| `text.py` | 从原始口碑确定性提取完整分析文本 | 摘要、情感判断 |
| `repository.py` | 任务、评论快照、候选方案、标注和缓存持久化 | 模型调用、Prompt 决策 |
| `service.py` | 单线程任务执行、检查点、重试和协作式控制 | FastAPI 响应、页面状态 |
| `api.py` | `/api/projects/{project_id}/review-analysis` 契约和状态码映射 | Prompt 内容、SQL 细节 |

依赖方向为：

```text
Review Analysis API → ReviewAnalysisService → ReviewAnalysisRepository
                                ├────────────→ ReviewAssetReader（只读评论资产）
                                ├────────────→ PromptRenderer
                                └────────────→ DeepSeekClient
```

`ReviewAssetReader` 只暴露已保存评论的查询和快照能力，不暴露汽车之家适配器。研究模块不得触发采集，也不得导入前端采集 workspace。

前端在 `frontend/src/modules/mcdm/review-analysis/` 中维护该页面的传输类型和状态，由 `McdmWorkbench.vue` 创建一次。采集模块与平台层均不得依赖该状态。

## 6. DeepSeek 配置与调用契约

### 6.1 环境文件

仓库提交 `.env.example`，实际 `.env` 继续由 `.gitignore` 排除：

```dotenv
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash
DEEPSEEK_REQUEST_TIMEOUT_SECONDS=120
```

用户只需在本机 `.env` 中填写 `DEEPSEEK_API_KEY`。启动脚本读取简单的 `KEY=VALUE` 行并注入子进程环境；不执行环境文件中的命令或表达式。Key 不返回给浏览器、不进入数据库、不出现在异常详情和日志中。

`DEEPSEEK_MODEL=deepseek-flash` 对应 DeepSeek-V4.1-Flash。修改模型名会形成新的结果谱系，缓存键必须包含实际模型标识。

### 6.2 HTTP 请求

- 使用项目已有 `httpx` 直接调用 `POST {base_url}/chat/completions`，不新增 OpenAI SDK。
- 使用 `response_format: {"type": "json_object"}`，Prompt 中明确包含 JSON 输出要求和完整示例。
- 首版显式关闭 thinking mode，避免保存或处理隐藏思维链，并降低逐评论任务的延迟与费用。
- 准则发现和归并设置与输出结构匹配的 `max_tokens`；逐评论标注使用更小上限。若 `finish_reason=length`、内容为空或 JSON 不完整，按无效响应处理。
- 保存 `prompt_tokens`、`completion_tokens`、`total_tokens` 和缓存命中 token 数；不在界面硬编码价格，避免价格变化造成错误费用承诺。

官方接口依据：

- 模型与基础地址：<https://api-docs.deepseek.com/quick_start/pricing/>
- JSON 输出：<https://api-docs.deepseek.com/guides/json_mode/>
- 思考模式控制：<https://api-docs.deepseek.com/guides/thinking_mode/>

## 7. Prompt 设计

Prompt 参考师姐代码的任务定义、示例和准则语义，但改造成可验证的工程契约。

### 7.1 准则发现 Prompt

第一阶段按字符预算和评论边界分批，每批输出：

```json
{
  "clues": [
    {
      "name": "空间实用性",
      "terms": ["后排不挤", "后备箱能装"],
      "evidence": ["后排坐三个成年人也不挤"]
    }
  ]
}
```

第二阶段聚合所有有效线索，输出最多 20 个候选准则，每个准则包含：

- `name`：唯一、明确的准则名称。
- `labels`：2～8 个从优到劣排列的唯一等级。
- `similar_terms`：用于人工理解的相关表达。
- `basis`：简短、可展示的归并依据，不是模型隐藏思维链。
- `evidence`：来自样本的代表性原文片段。

方案只保存为候选，不自动写入或冻结准则版本。

### 7.2 评论标注 Prompt

每次请求只处理一条完整评论，并携带冻结准则的名称、等级和顺序。输出契约为：

```json
{
  "annotations": [
    {
      "criterion": "空间实用性",
      "label": "宽敞灵活·全家舒适",
      "evidence": ["后排坐三个成年人也不挤"],
      "basis": "评论明确评价了后排乘坐空间"
    }
  ],
  "unmatched_evidence": []
}
```

约束如下：

- 一条评论可以命中零个、一个或多个准则。
- 同一准则在一条评论中最多出现一次；多段相关原文合并进 `evidence`。
- `criterion` 和 `label` 必须与冻结版本完全一致。
- `evidence` 必须是评论原文子串，不允许模型改写证据。
- 当同一准则同时出现褒贬信息时，模型依据整条评论给出最接近的单一等级，并在 `basis` 中简要说明冲突。
- 没有有效车辆评价时允许 `annotations=[]`，相关原文可进入 `unmatched_evidence`；空数组不是 API 异常的替代值。

### 7.3 Prompt 版本

首版使用 `criteria-discovery-v1`、`criteria-merge-v1` 和 `review-annotation-v1`。每次结果同时保存版本名和模板文件 SHA-256。修改模板正文必须提升版本号；只修改注释且模板哈希不变时无需提升。

## 8. 两阶段业务流程

### 8.1 准则发现

```text
选择自定义项目草稿和已采集车系
  ↓
预览评论数量与样本上限
  ↓
创建评论 ID / 内容哈希快照
  ↓
按车系分层并用稳定哈希排序选样
  ↓
分批提取 clues
  ↓
全局聚合并执行严格校验
  ↓
展示待审核准则方案
  ↓
研究人员编辑并应用到草稿
  ↓
沿用现有流程保存和冻结准则版本
```

样本选择不使用进程随机数。相同来源快照和相同样本上限必须产生相同样本顺序。界面默认上限为 1500 条，允许 1～5000 条；评论不足时使用全部评论。

### 8.2 评论级标注

```text
选择冻结的自定义准则版本
  ↓
选择已采集车系和验证条数/全部评论
  ↓
显示评论数、预计 API 调用数和外部传输提示
  ↓
用户确认后创建不可变评论快照
  ↓
按评论逐条调用、校验、保存检查点
  ↓
完成 / 部分失败 / 暂停 / 取消
  ↓
查询评论级结果和基础统计
```

界面提供 20、100、500 和“全部”四种范围。后端接受正整数上限或 `null` 表示全部，并始终以任务创建瞬间的评论快照为准。新增采集评论不会自动进入已创建任务。

## 9. 数据模型

### 9.1 `review_analysis_jobs`

- `id`
- `project_id`
- `schema_id`：准则发现可指向当前草稿；评论标注必须指向冻结版本
- `job_type`：`criteria_discovery`、`review_annotation`
- `status`：`queued`、`running`、`paused`、`completed`、`partial_failed`、`failed`、`cancelled`
- `phase`：发现任务为 `sampling`、`extracting`、`merging`；标注任务为 `annotating`
- `model`
- `prompt_manifest_json`：本任务实际使用的 Prompt 版本名与 SHA-256；发现任务同时记录提取和归并模板
- `schema_fingerprint`：评论标注必填
- `source_config_json`：选中车系、样本/数量上限和稳定排序规则
- `total_count`、`processed_count`、`success_count`、`failed_count`、`cache_hit_count`
- `input_tokens`、`output_tokens`、`cached_tokens`
- `control_requested`：`pause`、`cancel` 或空
- `last_error_code`、`last_error_message`
- `created_at`、`started_at`、`updated_at`、`finished_at`

同一时刻最多运行一个 LLM 任务，避免本机误启动多个高费用任务。只读查询不受此限制。

### 9.2 `review_analysis_job_reviews`

保存任务创建时的不可变评论清单：

- `job_id`
- `review_id`
- `series_id`、`series_name_snapshot`
- `content_hash`
- `ordinal`
- `status`：`pending`、`succeeded`、`failed`、`cached`、`skipped`
- `attempt_count`
- `annotation_id`
- `error_code`、`error_message`

唯一约束为 `job_id + review_id`。任务执行不得重新查询可变的“当前评论列表”决定范围。

### 9.3 `criteria_proposals`

- `job_id`，主键并关联发现任务
- `proposal_json`
- `proposal_fingerprint`
- `source_review_count`
- `sample_review_count`
- `applied_schema_id`、`applied_revision`
- `created_at`、`applied_at`

同一候选方案最多应用一次。应用时使用现有 `revision` 乐观锁；草稿已经变化则返回冲突，不能覆盖用户编辑。

`schema_fingerprint` 使用准则原始顺序和等级原始顺序构造的规范 JSON 计算 SHA-256；名称、等级或顺序任一变化都会改变指纹。

### 9.4 `review_annotation_results`

- `id`
- `content_hash`
- `schema_fingerprint`
- `model`
- `prompt_version`、`prompt_sha256`
- `result_json`
- `input_tokens`、`output_tokens`、`cached_tokens`
- `created_at`

唯一缓存键为：

```text
content_hash + schema_fingerprint + model + prompt_sha256
```

评论正文、准则顺序、等级顺序、模型或 Prompt 任一变化都会产生新结果；不能只用评论前 50 个字符或评论 ID 作为缓存键。

该表保存可复用的模型结果，不绑定某个评论 ID。`review_analysis_job_reviews.annotation_id` 把任务内的评论快照关联到结果；两条正文完全相同的评论可以安全复用同一结果，同时仍各自保留评论 ID、车系和任务顺序。

## 10. API 契约

统一前缀为 `/api/projects/{project_id}/review-analysis`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/sources` | 分页读取已采集车系及评论数量 |
| `POST` | `/discovery-jobs` | 创建准则发现任务 |
| `POST` | `/annotation-jobs` | 基于冻结版本创建评论标注任务 |
| `GET` | `/jobs` | 查询当前项目历史任务 |
| `GET` | `/jobs/{job_id}` | 查询任务进度、用量和错误摘要 |
| `POST` | `/jobs/{job_id}/pause` | 协作式暂停 |
| `POST` | `/jobs/{job_id}/resume` | 从检查点继续 |
| `POST` | `/jobs/{job_id}/cancel` | 协作式取消 |
| `POST` | `/jobs/{job_id}/retry-failures` | 为失败评论创建仅含失败项的新任务 |
| `GET` | `/jobs/{job_id}/proposal` | 读取待审核准则方案 |
| `POST` | `/jobs/{job_id}/proposal/apply` | 使用 revision 锁写入当前草稿 |
| `GET` | `/annotations` | 按任务、车系、准则、等级和状态分页查询 |
| `GET` | `/annotations/{annotation_id}` | 查看单条完整标注及来源元数据 |
| `GET` | `/summary` | 返回基础命中数和等级计数，不生成训练矩阵 |

关键状态码：

- 未配置 API Key：`503`，不创建任务。
- 项目、版本、任务或标注不存在：`404`。
- 准则发现目标不是可编辑草稿、评论标注目标不是冻结版本：`409`。
- 已有活动 LLM 任务、revision 冲突或任务状态不允许控制：`409`。
- 空选择、重复车系、无评论、非法上限或输出字段越界：`422`。
- DeepSeek 认证或余额问题：任务暂停并返回可操作错误摘要，Key 不回显。

## 11. 结果校验与错误处理

### 11.1 严格校验

- 准则候选必须满足现有准则上限：1～20 项，每项 2～8 个唯一非空等级，名称唯一。
- 评论标注的准则、等级、证据子串、字段长度、数组长度和重复项全部由 Pydantic 校验。
- `basis` 是简短判定依据，设定长度上限，不接受空字符串或长篇推理过程。
- 模型返回的额外字段被拒绝，避免接口漂移被静默吞掉。
- API 的成功 HTTP 状态不等于业务成功；空内容、截断、非法 JSON 和契约不符都属于无效响应。

### 11.2 重试和任务结果

- 网络超时、连接错误、`429` 和 `5xx` 最多重试 3 次，优先遵守 `Retry-After`，否则使用受限退避。
- `401`、`403`、余额不足或明确配置错误不连续重试；任务暂停，等待用户修复环境后继续。
- 单条评论在 JSON 或业务校验失败后最多重试 2 次，并在第二次 Prompt 中只附加结构修正提示。
- 单条评论最终失败时记录错误并继续下一条；任务最后为 `partial_failed`。
- 准则全局归并失败时没有可用候选方案，整个发现任务为 `failed`。
- 模型返回“没有相关准则”是合法成功结果；API 异常不得保存为空标注。

### 11.3 重启恢复

- HTTP 请求只负责创建或控制任务，不等待全部模型调用完成。
- 应用关闭采用协作式停止；当前请求完成后把任务保存为 `paused`。
- 非正常重启时，启动钩子把遗留 `queued/running` 任务转为 `paused` 并写入中断说明。
- 继续任务从第一个 `pending` 或可重试 `failed` 项开始，已经成功或命中缓存的评论不重复调用。

## 12. 页面设计

多准则工作台侧栏新增“评论语义分析”，页面保持当前研究工作台的文档化视觉风格，不复制评论采集页面的任务创建状态。

### 12.1 页面三段结构

1. **来源与准则版本**：当前项目、版本状态、已采集车系、评论数量和范围选择。
2. **分析任务**：准则发现或评论标注的创建、进度、暂停、继续、取消和用量统计。
3. **方案或结果**：发现任务展示可编辑候选方案；标注任务展示可筛选评论列表和详情。

### 12.2 准则发现交互

- 只有自定义项目的草稿版本可以接收候选方案。
- 创建前显示选中车系、可用评论数、样本上限和外部传输说明。
- 候选方案按准则逐项展示名称、等级、相关词、代表证据和归并依据。
- 用户可修改、增删和排序；“应用到草稿”不等于保存和冻结，应用后跳转现有准则工作台继续审核。
- revision 冲突时保留候选方案和页面编辑内容，并提示先刷新草稿，禁止静默覆盖。

### 12.3 评论标注交互

- 只有冻结的自定义准则版本可以启动。
- 创建前明确显示评论数量和预计 API 调用数；选择“全部”时再次确认。
- 结果列表显示车系、评论 ID、命中准则数、处理状态和时间。
- 详情展示原始评论、各准则等级、原文证据、简短依据及未匹配片段。
- 筛选只改变显示，不重新调用模型；重新分析必须显式创建新任务。
- 页面不得展示或下载 API Key，也不得把“模型完成”表述为“人工核验完成”。

## 13. 数据安全与研究可追溯性

- 页面在首次创建任务前明确提示：选中的公开评论文本会传输给 DeepSeek API 进行处理。
- API Key 仅存在于后端进程环境中；`.env`、数据库、运行日志、导出和 Git 均不得包含真实 Key。
- 普通日志只记录任务 ID、评论 ID、状态、耗时、错误类别和 token 用量，不记录完整评论、Prompt 或响应正文。
- 每条结果记录评论内容哈希、准则指纹、模型、Prompt 哈希和时间；项目导出后能够判断结果来自哪一次分析。
- 准则发现和标注都是模型辅助结果，不声称自动生成内容已经由专家验证。
- 本机服务继续只监听 `127.0.0.1`，没有鉴权时不得对公网开放。

## 14. 测试策略

### 14.1 后端

- 使用注入的假 DeepSeek 客户端测试成功、空内容、截断、非法 JSON、非法准则、非法等级和伪造证据。
- 测试完整原始评论到分析文本的确定性转换、顺序和去重。
- 测试分层稳定选样：相同快照和上限产生相同样本。
- 测试候选方案上限、等级顺序、重复名称和 revision 冲突。
- 测试评论快照不受后续采集变化影响。
- 测试缓存键在评论、准则、模型或 Prompt 变化时失效。
- 测试暂停、继续、取消、部分失败、失败项重试和进程中断恢复。
- 测试缺少 API Key 时不创建任务，认证错误不泄露 Key。
- 测试单进程活动任务互斥，历史和结果查询保持可用。
- 运行完整后端测试时不得访问真实 DeepSeek 或汽车之家。

### 14.2 前端

- 测试草稿与冻结版本对应操作的启用/禁用状态。
- 测试车系搜索、评论数量、样本/标注范围和“全部”二次确认。
- 测试任务轮询、控制、重启后暂停、部分失败和失败项重试。
- 测试候选方案编辑、应用和 revision 冲突保留。
- 测试按车系、准则、等级和状态筛选结果。
- 测试原文证据和未匹配片段的可读展示、键盘操作和窄屏布局。

### 14.3 联网验证

- 自动验证使用假客户端完成全流程，不需要真实 Key。
- 真实 API 冒烟由用户填写 `.env` 后显式运行，只选择少量已保存评论。
- 冒烟记录实际模型名、Prompt 版本、成功/失败数和 token 用量，不把真实评论正文或 Key 写入验收文档。
- 未配置 Key 时验证清晰的前置提示和现有非 LLM 功能不受影响。

## 15. 验收标准

1. 多准则系统具有独立“评论语义分析”页面。
2. 用户可以从已采集车系中选择准则发现和评论标注来源。
3. 准则发现采用分批线索提取和全局归并，并产生可审核候选方案。
4. 候选方案不能自动冻结或覆盖已冻结版本。
5. 评论标注只能绑定冻结的自定义准则版本。
6. 每条评论可以命中多个准则，每个命中项包含合法等级、原文证据和简短依据。
7. 模型不得创建冻结版本之外的准则或等级，未覆盖内容进入待补充线索。
8. 每条结果可追溯到评论哈希、准则指纹、模型和 Prompt 哈希。
9. API 异常、空响应和非法 JSON 不会被保存为空标注。
10. 已成功结果在暂停、重启或重试后不重复付费调用。
11. API Key 只从本机环境读取，不进入前端、数据库、日志或 Git。
12. 没有 API Key 时采集、归档浏览和人工准则编辑仍可正常使用。
13. 自动化测试完全离线；真实联网验证范围明确且可控制。
14. 运行须知、API 与数据契约、架构规范和验收记录与实现同步。

## 16. 实施与文档同步边界

实施顺序应保持依赖单向：

1. 建立评论文本转换、领域模型、Prompt 模板和假客户端测试。
2. 增加 DeepSeek 客户端、配置预检和严格输出校验。
3. 建立任务、快照、候选方案、标注和缓存仓储。
4. 实现准则发现与逐评论标注服务、控制和恢复。
5. 增加 API 契约与前端工作流。
6. 完成离线全量验证、少量真实 API 冒烟指引和文档同步。

需要同步更新：

- `.env.example` 和 `.gitignore` 的密钥边界。
- `AGENTS.md` 的评论分析模块职责与依赖方向。
- `docs/开发与架构规范.md` 的 LLM 客户端、任务和缓存边界。
- `docs/API与数据契约.md` 的任务、候选方案和评论标注契约。
- `docs/系统设计与实施路线.md` 的评论语义处理阶段。
- `docs/运行须知.md` 与 `README.md` 的环境配置、启动和真实冒烟说明。
- 新增实施验收记录，区分假客户端自动验证和真实 API 冒烟。

# 开发与架构规范

## 1. 目标与原则

本规范约束“观衡”新能源汽车研究平台的后续编码。优先级依次是：研究结论可追溯、业务口径正确、边界清楚、可测试、易于扩展。当前需求不需要的抽象、微服务、消息队列、权限模型或算法接口不提前建设。

- 单一事实来源：同一状态或口径只由一个模块拥有。
- 显式优于隐式：使用明确类型、版本、单位、数据来源和错误信息。
- 组合优于堆叠：入口层负责装配，业务规则、持久化和展示各自独立。
- 证据优于推断：只展示后端返回或有归档依据的数据；研究限制与指标同时出现。
- 兼容优于追新：先遵守锁定依赖和现有契约，再考虑框架新特性。

## 2. 总体依赖方向

```text
Platform router -> module registry
                -> Collection shell -> workspace + catalogFlow -> api.ts
                                                                   +-> Catalog router -> catalog service -> catalog repository
                                                                   |                  +-> Autohome discovery
                                                                   +-> Collection router -> collection service -> repository
                                                                                        +-> Autohome review adapter
                ExternalAccessCoordinator <------------------------- both services
                -> MCDM shell -> workspace -> api.ts -> HTTP routes
                                                     +-> domain rules
                                                     +-> Store (SQLite)
                                                     +-> Research (read-only archive)
                -> Adaptive planning page (no API yet)
```

入口可以依赖内层能力，内层不得反向了解入口：

- `domain.py` 不导入 FastAPI、SQLite 连接或文件系统路径。
- `store.py` 负责存取和事务，不决定准则是否合法或界面如何提示。
- `research.py` 适配已归档数据，不写入研究源文件，不承担在线训练。
- `collection/autohome.py` 只访问固定汽车之家目录/API 和明确允许的汽车之家静态资源域，不写数据库、不绕过验证；目录最终地址、页面标志及口碑分页元数据均需校验。
- `catalog_service.py` 负责编排目录发现、暂存和发布；`service.py` 负责编排评论采集、限速、重试和状态；两者必须通过同一个 `ExternalAccessCoordinator` 预约外部访问并在所有终态释放。
- `catalog_repository.py` 和 `repository.py` 不发网络请求。目录使用版本化暂存批次与原子活动指针；新评论任务使用规范化不可变快照，旧 `series_manifest` 只能作为历史任务兼容读取路径。
- Vue 页面不直接维护第二份跨页状态，也不绕过 `api.ts` 拼装重复的 HTTP 错误处理。
- 平台路由和模块注册表不得导入多准则 workspace、API 或业务页面内部状态。
- 自适应评估在材料与契约确认前只能保留规划页，不调用多准则接口或复用其结果。

FastAPI 版本锁定为 `0.128.8`，Pydantic 为 `2.12.2`。使用项目 `$fastapi` Skill 时，任何新 API 都要先确认此版本可用；不得仅因 Skill 或最新文档推荐而升级。

## 5. API 与数据契约

- HTTP 路径、字段、状态码和示例以 [API 与数据契约](API与数据契约.md) 为准；实现、TypeScript 类型和测试必须同时变化。
- 输入在边界处校验：字符串去除无意义空白；枚举、长度、范围和相互依赖条件显式表达；拒绝 NaN、Infinity 和结构不符的数据。
- 更新草稿必须携带 `revision`，冲突返回明确错误；不得静默覆盖并发修改。
- 准则版本冻结后只读。派生版本创建新标识与修订序列，旧数据保持原归属。
- 概率等级按 `L0`、`L1` 等键映射，不依赖 JSON 成员顺序；销量、份额和月度聚合的分母不得因界面搜索而变化。
- 时间、比例、销量、误差指标在接口和界面中保持单位一致。未知或不可用使用 `null`/空集合和说明，不用零冒充。
- 采集系统保存完整 `original_review`；摘要列表不得替代详情，研究模块不得修改原始对象。研究处理输出以评论 ID、车系 ID、内容哈希或快照时间关联。
- 当前目录以 `active_batch_id` 为唯一发布事实来源；发现过程只能写暂存批次，成功发布前不得清空或覆盖旧目录。
- 新任务必须在同一事务中校验活动目录并写入 `collection_job_series`；任务运行只读该快照，不受后续目录刷新影响。升级前任务可读取 `series_manifest`，但不得把它继续作为新写入格式。

## 6. 研究数据与结果真实性

- 原研究压缩包、归档文件和衍生清单通过 SHA-256 建立来源链。
- 归档指标必须标记为“原研究结果”，不得描述为当前服务实时计算或重新验证。
- 训练/测试时间重叠、自然语言标签缺失等已知限制必须随相应结果可见。
- 新算法接入时建立独立的模型版本、数据版本、参数和运行记录；不得覆盖原归档结果。
- 导入文件设大小、编码和 schema 限制。文件名只作显示信息，不直接构造任意服务器路径。

## 7. 错误、日志与安全边界

- 向用户返回可行动的中文错误；服务器内部异常不得泄漏堆栈、绝对路径、SQL 或敏感配置。
- 可预期的校验失败使用 4xx；服务内部错误使用 5xx。不要用成功状态包装失败。
- 日志记录事件、资源标识和结果，不记录整份评论、上传内容或未来可能加入的凭据。
- 汽车之家目标域名由服务端固定允许列表约束；403、429 或验证页面立即暂停。Cookie 只存在于临时会话，不写数据库、日志或导出。
- 当前系统没有用户鉴权，仅允许本机监听。若要局域网/公网部署，必须先完成身份认证、授权、CSRF/CORS、上传隔离、速率限制、TLS 终止与威胁建模。
- 明确的安全审查读取 `$security-best-practices` 中与 FastAPI 和 Vue 对应的参考；重大暴露面变更使用 `$security-threat-model`。

## 8. 命名、依赖与版本

- Python：模块、函数和变量使用 `snake_case`，类型/模型使用 `PascalCase`；TypeScript：变量/函数使用 `camelCase`，组件和类型使用 `PascalCase`。
- 名称表达业务含义，避免 `data2`、`manager`、`helper`、`common` 等无法说明所有权的词。
- 新依赖必须说明现有标准库/已安装依赖为何不能满足、运行与许可证影响、锁定版本和移除路径。
- 不引入仅为少量格式化、映射或包装而存在的依赖。依赖升级单独成变更并运行完整门禁。
- 秘钥和环境差异不得写入源码；如新增环境变量，同步运行文档并提供无敏感值示例。

## 9. 何时记录 ADR

以下变化在 `docs/ADR/` 建立决策记录：更换数据库或前后端框架、改变部署/鉴权边界、引入异步任务或模型运行平台、改变核心数据版本策略、引入不可逆的数据迁移。局部重命名、样式调整和已有规则内的小重构不补造 ADR。模板见 [ADR 说明](ADR/README.md)。

## 10. Git 版本管理

### 10.1 仓库与主分支

- 规范远端为 `origin = git@github.com:Hyise/NEV-agent-systems.git`，默认分支为 `main`。开发机必须使用已登记到 GitHub 账户的 SSH 密钥，不在仓库内保存私钥。
- `main` 始终代表已通过适用质量门禁、可以演示的版本。具备 GitHub 管理权限后，应启用分支保护，要求 Pull Request 和必要检查通过后再合并。
- 禁止对共享 `main` 强制推送、重写历史或直接提交未经验证的试验代码。确需修复历史中的凭据时，先停止传播并单独制定清理方案。

### 10.2 分支命名

从最新 `main` 创建短生命周期主题分支，使用小写英文、数字和连字符：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feature/` | 新业务能力 | `feature/report-export` |
| `fix/` | 缺陷修复 | `fix/schema-revision-conflict` |
| `refactor/` | 不改变外部行为的重构 | `refactor/split-api-router` |
| `docs/` | 仅文档或软著材料 | `docs/software-manual` |
| `test/` | 测试基础设施或补充覆盖 | `test/import-boundaries` |
| `chore/` | 工具、依赖和仓库维护 | `chore/update-vite` |

一个分支只解决一个可说明的问题。持续时间较长的研究试验不要直接堆积在 `main`；先明确数据、算法和输出边界。

### 10.3 提交规范

提交信息采用 Conventional Commits 的轻量格式：

```text
type(scope): 简洁说明
```

允许的 `type` 为 `feat`、`fix`、`docs`、`refactor`、`test`、`perf`、`build`、`ci`、`chore`。`scope` 使用稳定模块名，例如 `backend`、`frontend`、`criteria`、`research`、`docs`；无法准确归类时可以省略。

示例：

```text
feat(criteria): 支持从冻结版本派生准则草稿
fix(import): 拒绝包含非有限概率的CSV
docs(architecture): 补充Git版本管理规范
```

- 每个提交保持原子性：实现、对应测试和必要文档一起提交，避免混入无关格式化。
- 提交正文用于解释“为什么”和兼容影响，不逐行复述代码。
- 提交前检查 `git diff --check` 和 `git status --short`，确认没有凭据、运行数据、临时文件或意外的大文件。
- 不使用 `--no-verify` 绕过已经配置的门禁；不提交注释掉的调试代码或虚假的测试结果。

### 10.4 Pull Request 与合并

Pull Request 至少写明：问题背景、主要变化、验证命令及结果、数据/API/文档影响、已知限制；视觉变化附真实运行截图。审查中发现的关键和重要问题在合并前处理，无法处理的风险要明确记录并经维护者接受。

主题分支默认采用 squash merge，使 `main` 保持一个需求一个可回退提交；需要保留有意义的多提交演进时可使用普通合并。禁止在未理解差异时解决冲突，也不得用强推覆盖他人提交。

### 10.5 版本与标签

- 应用版本使用语义化标签 `vMAJOR.MINOR.PATCH`。当前 `0.x` 阶段，新能力递增 `MINOR`，兼容性缺陷修复递增 `PATCH`；尚未稳定的接口可以变化，但必须记录迁移影响。
- 仅对通过完整质量门禁并具有对应验收记录的提交创建带注释标签，例如 `git tag -a v0.1.0 -m "阶段一可运行版本"`。
- 标签创建后不移动或复用。错误发布通过新补丁版本修正；不得静默重打同名标签。
- 软件著作权提交节点可额外建立清晰的发布说明，但代码版本仍使用同一标签体系，避免出现无法对应源码的“材料版”。

### 10.6 纳入与排除版本控制的内容

必须纳入：应用源码、测试、数据库 schema/迁移、依赖锁定或版本清单、启动脚本、`AGENTS.md`、项目 Skill、设计/API/运行/验收文档。

不得纳入：`node_modules/`、`frontend/dist/`、`.runtime/`、pytest 缓存、浏览器输出、虚拟环境、`.env*`、SQLite 运行库，以及 `backend/data/` 和 `algorithms/reference/` 下由归档脚本生成的研究副本。必要的来源、哈希和生成方式用脚本与文档记录。

未来确需保存无法重建的大型二进制或数据集时，先评估数据许可与隐私，再使用 Git LFS 或独立制品存储；不得直接把大文件塞入普通 Git 历史。

### 10.7 GitHub SSH 密钥管理

当前开发机为本仓库使用独立的 Ed25519 密钥：

- 私钥路径：`$env:USERPROFILE\.ssh\id_ed25519_nev_agent_systems`
- 公钥路径：`$env:USERPROFILE\.ssh\id_ed25519_nev_agent_systems.pub`
- 当前公钥指纹：`SHA256:GvcgPWY8e+4vr++xYlxbtBtlmjWAbbaj7o+kzjTN9ww`
- 密钥注释：`nev-agent-systems@Hyise`

私钥只能保存在开发机用户目录，依赖操作系统 ACL 保护，禁止复制到仓库、文档、聊天、日志、网盘或构建产物。项目文档只记录路径和指纹，不记录私钥内容。公钥可以提交给 GitHub，但不应把个人公钥硬编码为项目运行依赖。

   ```powershell
   ssh-keygen -lf "$env:USERPROFILE\.ssh\id_ed25519_nev_agent_systems.pub" -E sha256
   ```

4. 首次连接时将终端显示的 GitHub 主机指纹与 GitHub 官方文档核对，不使用 `StrictHostKeyChecking=no` 绕过验证。

   ```powershell

   git config core.sshCommand "ssh -i $key -o IdentitiesOnly=yes"
   ```

# 评论语义分析模块边界

`backend/review_analysis/` 采用单向依赖：`api → service/pipeline → repository/client`，领域模型、文本转换和 Prompt 渲染保持纯函数或纯契约。仓储保存任务创建时的 `analysis_text`，运行时不得重新读取当前评论正文替换快照。结果缓存键固定为 `content_hash + schema_fingerprint + model + prompt_sha256`。

DeepSeek 客户端只使用 `httpx` JSON 模式，不记录 Authorization、完整 Prompt、评论正文或响应正文。准则发现采用完整评论边界的分批线索与一次全局归并；评论标注一条评论一次请求，封闭在冻结体系内。单进程最多一个活动 LLM 任务，控制在相邻调用之间协作生效。

成功的准则发现批次必须原子保存线索、进度与用量，恢复任务时不得重复调用已完成批次或已保存的全局归并；模型证据必须非空并逐项验证为某一条任务评论快照的原文子串。单项证据不可追溯时只丢弃该证据，没有剩余证据的线索或候选准则不得保存；归并阶段逐项校验、按名称保留首次出现项并限制为 20 个，整批无有效结果时仍拒绝。任务创建时保存 Prompt 版本/哈希、模型和草稿 revision，运行或应用阶段发现谱系变化必须中止并提示重建任务。所有任务读取与变更接口都要同时校验 `project_id`，不得仅凭任务 ID 操作。工作器从 queued 进入 running、以及最后一次请求后的完成/暂停/取消都必须使用数据库原子状态转换。控制请求的优先级固定为取消高于暂停：已登记的取消不得被随后到达的暂停覆盖，工作器读取控制请求时必须在同一事务中消费请求并落定终态。

前端 `review-analysis/workspace.ts` 是该页面唯一状态源，由 `McdmWorkbench.vue` 创建一次。页面组件不创建 workspace，不导入采集模块内部状态，筛选结果不得触发新的模型调用。已完成任务必须仍可从历史列表进入候选审核或结果查询；选择“全部评论”执行前必须显示跨页选择的评论总数并二次确认。项目或准则版本切换必须清空详情和筛选，并以代际标识阻止旧异步响应覆盖新上下文。
